# 웹 패널

[Runquill README](../README.ko.md) · [English](panel.md)

패널은 매니저가 `RUNQUILL_PANEL_ADDR`에서 제공하는 단일 페이지입니다. 설정 방법은 [웹 패널과 팀 권한](operations.ko.md#웹-패널과-팀-권한)을 참고하세요. 이 가이드는 각 화면이 무엇을 보여 주고 누가 쓸 수 있는지 설명합니다. 패널이 호출하는 모든 경로는 [API 명세](../api/openapi.yaml)에 있습니다.

## 화면 이동

화면은 `#/queue`처럼 URL 프래그먼트로 구분합니다. 알 수 없는 화면이나 내 역할로 열 수 없는 화면을 열면 볼 수 있는 첫 화면으로 돌아갑니다.

| 그룹 | 화면 | 필요한 역할 |
| --- | --- | --- |
| 운영 | 개요, 대기열, 작업 기록, 러너, 호스트와 풀, 사용량, 로그 | Viewer |
| 관리 | 마이그레이션, 백업, 감사 기록, 설정 | Admin |
| 관리 | 팀과 토큰 | Viewer(팀 목록은 Admin만) |

사이드바에는 대기 중인 작업, 실행 중인 러너, 오프라인 호스트 수가 표시됩니다.

- **개요**는 용량, 호스트 상태, GitHub 연결, 첫 작업 점검 목록, 가장 오래 기다린 작업을 요약합니다.
- **대기열**은 대기 중, 배정됨, 최근 정리된 작업을 저장소, 작업 ID, 풀로 필터링해 보여 줍니다. 풀 열에는 작업이 `os__NAME__`으로 고른 러너 OS가 함께 표시됩니다. 작업을 선택하면 러너 라벨, 러너 OS와 이미지, 단계별 소요 시간 막대와 단계마다의 시간, `GET /api/jobs/{id}`에서 가져온 CPU·메모리 측정값, 현재 대기 또는 시작 상태 설명을 볼 수 있으며, 러너 이미지를 기다리거나 메모리 부족으로 종료된 경우(`runner_memory_limit`)도 여기에 표시됩니다. 관리자는 **작업이 보이지 않나요?**에서 저장소 점검(`POST /api/diagnose`)을 실행할 수 있습니다.
- **작업 기록**은 7일간의 작업 기록을 저장소, 결과, 시간으로 필터링해 보여 줍니다. 풀 열에는 작업이 고른 러너 OS가 함께 표시됩니다. 작업 ID를 선택하거나 `#/jobs?job=ID`를 열면 발견부터 실행까지의 단계별 소요 시간과, 한도 대비 CPU·메모리 최고 사용량, 메모리 부족 종료 여부를 볼 수 있습니다. 리소스는 `local` Docker 호스트에서만 측정하므로, 다른 작업에는 측정값이 없다고 표시됩니다.
- **러너**는 최신 스냅샷의 러너 컨테이너나 Pod를, 각 러너가 맡은 작업의 러너 이미지와 OS, 러너를 준비한 시각과 함께 보여 줍니다. Operator와 Admin에게는 `local`이나 `ssh://` 호스트의 러너마다 **로그** 화면의 해당 로그로 가는 링크(`#/logs?runner=NAME`)를 보여 줍니다.
- **호스트와 풀**은 호스트 상태, 슬롯, 풀 용량을 보여 주고, 운영자가 배정을 일시 중지하거나 재개할 수 있게 합니다. 매니저가 [러너 이미지를 받는](runner-images.ko.md#이미지-자동-받기) 동안에는 `local`과 `ssh://` 호스트마다 이미지가 준비됐는지, 없는지, 받는 중인지, 받지 못했는지와 받기 오류도 표시합니다. [웜 러너](workers.ko.md#러너를-미리-띄워-두기)를 쓰는 풀의 호스트에는 풀의 `warm` 설정 대비 대기 중인 웜 러너 수가 표시되고, 풀 표에 그 합계가 나옵니다. [탄력적 한도](elastic-limits.ko.md)를 켜면 `GET /api/elastic`에서 가져온 모드, 호스트별 여유분, 최근 크기 조정 결정도 보여 줍니다. **서버 자원**은 [아래](#서버-자원)에서 설명합니다.
- **사용량**은 [사용량 통계](#사용량-통계)를 날짜, 저장소, 풀, 호스트별 차트로 보여 주고, [리소스 적정성](#리소스-적정성) 판정을 보여 줍니다.
- **로그**는 Operator와 Admin에게 [러너 로그](#러너-로그)를 실시간으로 보여 줍니다.
- **마이그레이션**은 관리자가 [워크플로 이전](workflow-migration.ko.md)을 단계별로 진행하게 합니다.
- **백업**은 [예약 백업](backups.ko.md) 설정과 마지막 실행을 보여 주고 대기열 백업을 내려받습니다. 복구는 명령줄에서만 합니다.
- **감사 기록**은 감사 대상 작업을 작업 종류와 실행한 사람으로 필터링해 보여 줍니다.
- **팀과 토큰**에서는 모든 사용자가 API 토큰을 관리하고, 관리자는 팀원도 관리합니다.
- **설정**에서는 전체 한도, 폴링 주기, 러너 이미지, Docker 워커와 풀(각 풀이 허용하는 러너 OS 이름과 `warm`, `warm_max_idle_minutes` 설정 포함)을 바꾸고 재시작 없이 적용합니다. [러너 이미지 목록](runner-images.ko.md#러너-이미지-목록)은 읽기 전용으로 보여 줍니다. 아웃바운드 `agent://` 워커는 `RUNQUILL_DOCKER_HOSTS`에서만 정합니다. 시작할 때 배포 설정이 저장된 설정과 맞지 않으면 매니저는 배포 설정의 `agent://` 워커를 쓰고, 더는 없는 워커를 가리키는 한도와 풀 항목을 뺍니다. 저장된 설정에 없는 `agent://` 워커는 배포 설정의 한도와 풀을 그대로 씁니다. 그래도 적용할 수 없는 저장된 설정은 매니저 시작을 막으므로, 저장된 풀 제한이 사라지는 일은 없습니다. 바뀐 내용은 하나씩 로그에 남고 `runquill doctor`에도 표시됩니다. 저장된 값은 **설정**을 다시 저장할 때까지 바뀌지 않습니다.

대기열 진단은 스냅샷, 작업 기록 API, CLI, 읽기 전용 MCP에서 같은 원인 코드를 씁니다. 이 코드는 워커 가용성, 저장소 한도, 이미지 준비, 배정을 구분합니다. 새 작업에는 Runquill이 JIT 등록을 요청한 시각, GitHub가 이를 반환한 시각, 워커 런타임이 실행을 받아들인 시각도 기록됩니다. Kubernetes는 Pod를 만들 때 실행을 받아들인 것으로 봅니다. 그 뒤 GitHub가 시작을 보고하기까지의 시간에는 Pod 스케줄링과 이미지 받기가 포함될 수 있습니다. 이전 릴리스의 작업은 당시 Runquill이 기록한 시각만 표시합니다.

## 역할과 토큰

| 작업 | Viewer | Operator | Admin |
| --- | --- | --- | --- |
| 운영 화면 보기, `fleet:read` 토큰 만들기 | 예 | 예 | 예 |
| 호스트 일시 중지·재개, 대기 중인 작업 취소·재시도, `hosts:write`와 `jobs:write` 토큰 만들기 | | 예 | 예 |
| 러너 로그 보기(로그인한 세션만) | | 예 | 예 |
| 팀, 감사 기록, 설정, 마이그레이션, 백업, 대기열 백업 다운로드, 저장소 점검 | | | 예 |

토큰에는 범위가 정확히 하나 있고, 그 범위의 경로만 호출할 수 있습니다. `hosts:write`나 `jobs:write` 토큰으로는 운영 현황을 읽을 수 없습니다. 러너 로그, 워크플로 이전, 백업처럼 브라우저 전용이거나 관리자 전용인 경로에는 어떤 토큰도 쓸 수 없습니다.

| 범위 | 경로 |
| --- | --- |
| `fleet:read` | `GET /snapshot`, `GET /api/events`, `GET /api/jobs`, `GET /api/jobs/{id}`, `GET /api/elastic`, `GET /api/hosts/resources`, `GET /api/usage`, `GET /api/usage/rightsizing`, `POST /mcp` |
| `hosts:write` | `POST /api/hosts/cordon` |
| `jobs:write` | `POST /api/jobs/{id}/cancel`, `POST /api/jobs/{id}/retry` |

## 서버 자원

**호스트와 풀** 화면의 **서버 자원** 표는 `GET /api/hosts/resources`에서 가져옵니다. 모든 역할과 `fleet:read` 토큰이 읽을 수 있습니다. 숫자는 모두 매니저가 이미 가진 데이터에서 옵니다. 화면을 열어도 호스트에서 명령을 실행하지 않습니다. 다만 매니저가 시작하거나 설정이 바뀐 뒤 아직 읽지 않은 호스트에는 엔진 `info`를 한 번 호출합니다. 엔진이 응답하지 않은 호스트는 최대 30초에 한 번만 다시 묻습니다.

| 열 | 출처 |
| --- | --- |
| CPU 수, 메모리 | 엔진의 `info` 보고입니다. 매니저는 러너를 배치하려고 호스트마다 한 번 읽고 그 값을 유지합니다. |
| 사용 중인 슬롯 | 전체 스냅샷에서 호스트 슬롯 한도 중 차지되거나 예약된 슬롯입니다. |
| 예약된 CPU, 예약된 메모리 | 슬롯을 차지한 러너에게 약속된 자원입니다. 풀의 `cpus`와 `memory_mib`에 차지된 슬롯 수를 곱합니다. [탄력적 한도](elastic-limits.ko.md)가 호스트를 측정하면 러너의 현재 한도를 씁니다. 한도가 없는 풀은 **제한 없음**으로 표시합니다. |
| 러너 사용량 | 탄력적 한도 점검의 마지막 측정값입니다. `RUNQUILL_ELASTIC`을 설정하고 풀에 `cpus`나 `memory_mib`가 있을 때 `local` 호스트에만 표시하며, 그 밖에는 **측정 안 됨**으로 표시합니다. |
| 디스크 | 호스트에 남아 있는, Runquill이 받은 러너 이미지와 러너 캐시 볼륨입니다. `docker system df -v`와 `image inspect`로 잽니다. |

`docker system df -v`는 모든 볼륨을 훑기 때문에, 디스크 사용량은 누군가 **디스크 사용량 측정**(`GET /api/hosts/resources?disk=1`)을 선택할 때만 잽니다. 모든 사용자를 통틀어 측정은 한 번에 하나만 실행되고 결과는 10분 동안, 측정하지 못한 호스트가 있으면 1분 동안 유지됩니다. 3초보다 오래 걸리는 측정은 백그라운드에서 끝나고, 패널이 결과를 다시 요청합니다. Podman은 볼륨 크기를 가볍게 잴 수 없어서 캐시 크기를 **크기 알 수 없음**으로 표시합니다.

매니저는 아웃바운드 `agent://` 워커와 Kubernetes 노드를 읽을 수 없습니다. 이들의 용량, 사용량, 디스크는 0 대신 **확인할 수 없음**으로 표시합니다. `agent://` 워커의 예약량은 풀 설정에서 오므로 계속 표시합니다. 엔진이 응답하지 않는 `local`이나 `ssh://` 호스트는 용량 대신 오류를 표시합니다.

## 명령 팔레트와 테마

macOS에서는 Cmd+K, 그 밖의 환경에서는 Ctrl+K를 누르거나, 입력란 밖에서 `/`를 누르면 명령 팔레트가 열립니다. 팔레트에는 열 수 있는 화면, 현재 화면의 명령, 언어와 테마 전환, 새로고침과 로그아웃이 나오고, 검색어를 입력하면 일치하는 러너, 작업, 호스트도 나옵니다. 방향키, Page Up과 Page Down, Enter, Esc로 조작합니다.

테마는 기본적으로 시스템 설정을 따릅니다. 상단 막대나 팔레트에서 **밝게** 또는 **어둡게**를 고를 수 있습니다. 선택한 값은 브라우저에 `runquill-theme`으로 저장됩니다. 언어는 브라우저 설정을 따르며, English나 한국어를 직접 고르면 `runquill-language`에 저장됩니다.

## 실시간 갱신

패널은 운영 현황 스냅샷을 보내는 Server-Sent Events 스트림인 `GET /api/events`를 구독합니다. 매니저는 2초마다 변경을 확인하고, 15초마다 연결 유지 신호를 보내며, 스트림을 10분마다 닫아 브라우저가 다시 연결하면서 권한을 다시 확인하게 합니다. 매니저 하나는 전체 64개, 사용자당 4개의 스트림을 받습니다.

스트림이 10초 안에 다시 열리지 않거나 서버가 거부하면 패널은 3초마다 `GET /snapshot`을 폴링하고, 매니저에 연결할 수 없는 동안에는 간격을 최대 30초까지 늘립니다. 60초 뒤에는 스트림을 다시 시도합니다. 상단 막대의 표시는 **실시간**, **폴링 중**, **다시 연결 중**, **연결 끊김**, **탭이 숨겨져 일시 중지됨** 중 하나입니다.

## 사용량 통계

사용량은 끝난 작업의 작업 수, 실패, 러너 사용 시간, 대기 시간을 셉니다. 각 작업은 끝난 UTC 날짜에 한 번만 집계하며, 날짜, 저장소, 풀, 호스트별로 묶습니다.

- **실패**는 Runquill이 작업을 포기했거나(24시간 동안 시작하지 못함) 패널에서 취소한 경우입니다. GitHub의 작업 결과와는 다릅니다.
- **러너 사용 시간**은 러너 준비부터 러너 정리까지입니다.
- **대기 시간**은 대기열에 들어간 때부터 러너 준비까지이며, 러너를 받지 못한 작업은 실패 처리될 때까지입니다. 중앙값과 95번째 백분위수는 고정된 히스토그램 구간으로 추정합니다.

스케줄러는 7일간의 작업 기록에서 작업이 삭제되기 전에 끝난 작업을 일별 합계에 반영합니다. 일별 합계 행은 400 UTC일 동안 보관하며, 요청 하나는 최대 400일을 다룹니다. 합계는 대기열 데이터베이스에 있지만 대기열 백업에는 포함되지 않으므로, 복구한 대기열의 통계는 비어 있는 상태로 시작합니다.

## 리소스 적정성

**사용량**의 **리소스 적정성** 표는 `runquill usage --rightsizing`과 같은 보고서인 `GET /api/usage/rightsizing`에서 가져옵니다. 풀 또는 워크플로 작업별 묶음과 1~7일 기간을 고릅니다. CPU와 메모리마다 측정된 가장 높은 최고 사용량을 가장 최근 작업의 한도와 비교해 판정합니다. **부족**(최고 사용량이 한도의 80% 초과이거나 메모리 부족 종료), **과다**(측정된 작업 3개 이상에서 최고 사용량이 모두 한도의 25% 미만), **적정**, **작업 부족**, **한도 없음** 중 하나입니다. 러너를 측정한 작업만 세며, 지금은 `local` Docker 호스트가 해당합니다.

## 러너 로그

Operator와 Admin은 현재 작업을 맡은 러너의 컨테이너 출력을 볼 수 있습니다. GitHub 단계 로그가 아니라 러너 프로세스의 출력(`docker logs --timestamps`, `RUNQUILL_CONTAINER_ENGINE=podman`이면 `podman logs`)이며, 단계 로그는 GitHub에 남습니다. 조회할 때마다 `runner.logs`로 감사 기록에 남습니다.

- `local` Docker 호스트와 `ssh://` 호스트의 러너만 지원합니다. Kubernetes와 `agent://` 러너는 로그를 볼 수 없다고 응답합니다.
- 요청 하나는 최근 2000줄까지 반환하거나, 최대 15분 동안 새 줄을 이어서 받습니다. 출력은 8 MiB에서 멈추며, 러너 인증 정보를 한 번 더 보호하기 위해 200자 이상 이어진 base64 문자는 `[redacted]`로 바꿉니다.
- 로그 요청은 동시에 최대 8개까지 실행합니다. API 토큰으로는 로그를 읽을 수 없습니다.
- 매니저는 `RUNQUILL_CONTAINER_ENGINE`이 선택한 CLI로 로그를 읽고, `ssh://` 호스트에는 러너를 시작할 때와 같은 방식으로 접속합니다.

러너 로그 스트리밍은 가짜 엔진 명령으로만 테스트했습니다. 실제 운영 환경에서는 아직 실행하지 않았습니다.
